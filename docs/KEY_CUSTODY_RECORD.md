# Key custody record

**Print this. Complete it by hand. Keep the signed original with the company
secretary.** It is the evidence that build-plan §2.2 was actually done, as
opposed to intended — and it is what an auditor, or a new ICT manager on their
first day, will ask to see.

> **Two secrets in this system cannot be recovered by anyone, including their
> vendor, including Anthropic, including the person who generated them.** There
> is no reset link and no support ticket. That is deliberate — it is the trade
> that keeps them out of the database — and it is why they are escrowed the way
> a bank mandate is escrowed rather than the way an API key is.

---

## 1. What is held

| # | Secret | What it protects | What its loss costs |
|---|---|---|---|
| **K1** | `GATEWAY_CREDENTIAL_KEY` | the AES key for every organisation's stored payment-gateway credentials (`lib/gateway/credentials.ts`) | **Every org's gateway credentials become permanently unreadable.** Each org must re-enter its Paystack/Flutterwave details. No org can take an online payment until it does. |
| **K2** | Backup passphrase | every encrypted backup taken with `npm run backup -- --encrypt` | **Every encrypted backup becomes random bytes.** The Supabase daily backups survive, so this is not total — but the off-site copies, which exist precisely for the case where Supabase is unreachable, are gone. |

⚠️ **K1 and K2 never share an envelope, a safe, or a sentence in an email.**
They protect different things and a single theft must not take both.

⚠️ **K2's envelope is never stored with the media holding the backups.** An
encrypted drive and its passphrase in the same drawer is an unencrypted drive.

---

## 2. Sealing procedure

Do this once per secret, with **two people present**. It takes about ten
minutes.

1. **Generate at the destination.** On the machine that will set it — never a
   shared or borrowed one:
   ```
   node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
   ```
   For **K1**, confirm it decodes to 32 bytes before trusting it, because
   `credentials.ts` refuses anything else:
   ```
   node -e "console.log(Buffer.from('PASTE','base64').length)"   # must print 32
   ```
2. **Put it to work first**, so you never seal a value that turns out to be
   wrong. K1 → the Vercel environment variable. K2 → used once in a real
   `npm run backup -- --encrypt`, and the resulting file decrypted back.
3. **Write it out twice, by hand or printed**, one copy per envelope. Block
   capitals. `0`/`O` and `1`/`l`/`I` are the characters that get mis-copied at
   3am — write them unambiguously, and mark the character count on the slip.
4. **Seal both envelopes.** On each: the secret's label (K1 or K2), the date,
   and **nothing that identifies what it opens** — an envelope marked
   "production payment key" tells a thief what they have found.
5. **Sign across the seal**, both people, so tampering is visible.
6. **Separate them.** Envelope A → the company safe. Envelope B → a **named
   director**, in a different building. Never both in one office.
7. **Clear the traces.** Close the terminal, clear the scrollback, and delete
   any file you pasted it into. Never a chat window, a ticket, a WhatsApp
   message, or an email — not even to yourself.
8. **Complete §3 below and file this record.** The record names the holders; it
   never contains the secret.

## 5. Recovery procedure

**Two people, always.** One opens, one witnesses and records.

1. Record in §6 **before** opening: the date, who, and why.
2. Open **Envelope A** if reachable; Envelope B only if it is not.
3. Use the value. Do not photograph it, message it, or type it into anything
   other than the field it is for.
4. **The seal is now broken, so the secret is treated as exposed.** Re-seal it
   the same day, per §2 steps 3–7, in fresh envelopes with fresh signatures.
5. If it was opened because it was *lost* elsewhere, re-seal is not enough —
   see §7.

## 7. Rotation

**K1 cannot be rotated quietly.** Changing `GATEWAY_CREDENTIAL_KEY` makes every
stored credential unreadable, exactly as losing it would. Rotation therefore
means: generate the new key, set it, and have **every organisation re-enter its
gateway credentials**. Plan it as an operation with notice given, never as
maintenance. Rotate only on actual or suspected exposure.

**K2 rotates cheaply.** Take a fresh `--encrypt` backup under the new
passphrase and destroy the old copies. Keep the old passphrase sealed until
every file encrypted under it has been destroyed — not before.

## 8. Never

- Never in a chat window, an AI session, a ticket, an email, or a screenshot.
- Never in the repository, a `.env` committed by accident, or a build log.
- Never both secrets in one envelope, one safe, or one message.
- Never K2 stored with the drive holding the backups.
- Never a single holder — one person leaving must not take the system with them.
- Never "we'll write the record later". The record is the control; the envelope
  is only where the paper lives.
